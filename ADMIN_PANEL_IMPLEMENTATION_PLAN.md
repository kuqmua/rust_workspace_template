## Подробный план

### 1. Зафиксировать границы административного модуля

Административная часть не должна знать о географии. Из Mapcam не переносить:

- PostGIS;
- проекты и группы проектов;
- слои и группы слоёв;
- геометрические объекты;
- свойства и значения объектов;
- тайлы;
- WFS;
- карты;
- камеры;
- скриншоты;
- географические поля системных настроек.

Оставить общую модель:

```text
auth
users
roles
permissions
user_roles
role_permissions
sessions
login_attempts
audit_log
system_settings
metrics
openapi
```

### 2. Разделить административную логику по архитектурным границам

Общую логику следует вынести из бинарного `server`.

Предлагаемая структура:

```text
server
  только запуск, конфигурация и сборка общего Router

server_admin
  административные таблицы
  бизнес-логика
  API
  авторизация
  RBAC
  аудит
  OpenAPI

server_admin_frontend
  SPA
  статические ресурсы
  маршруты страниц
```

Если нежелательно создавать два crate, минимальный вариант — один `server_admin`, содержащий API и frontend. Разделение backend и frontend предпочтительнее.

Создание новых crate и добавление зависимостей должно быть явно разрешено при переходе к реализации.

### 2.1. Сделать текущие proc-macro основой реализации

Админку следует строить с обязательным переиспользованием существующих proc-macro workspace. Ручная реализация типового CRUD, PostgreSQL-wrapper типов, конфигурационных getter, OpenAPI-схем и клиентских контрактов не допускается, если соответствующая возможность уже есть в генераторах.

Матрица использования текущих proc-macro:

| Proc-macro | Применение в админке |
|---|---|
| `gen_pg_types::gen_pg_types!` | PostgreSQL-wrapper типы идентификаторов, временных значений, nullable/non-null полей и других стандартных SQL-представлений |
| `gen_pg_tbl::GenPgTbl` и атрибуты `gen_pg_tbl` | Таблицы пользователей, ролей, разрешений, связей, сессий, аудита и настроек; CRUD, SQL, DTO, Axum routes, OpenAPI и клиентские функции |
| `gen_wh_flts::gen_wh_flts!` | Общая генерация операторов фильтрации; напрямую расширяется только при появлении отсутствующего оператора |
| `newtype::Newtype` | `From`, `TryFrom`, `AsRef`, borrowing helpers и другие типовые реализации для доменных wrapper-типов |
| `newtype::BoundedString` | Логины, отображаемые имена, названия ролей, permission name и ограниченные текстовые поля |
| `newtype::EnumFromStr` | Разбор permission, audit action, audit resource и других закрытых enum из строкового представления |
| `try_from_env::TryFromEnv` | Чтение JWT, cookie, session, bootstrap и rate-limit конфигурации из environment |
| `gen_getter_traits_for_struct_fields` | Генерация минимальных getter traits для конфигурации и application state |
| `server_app_state_macros::impl_cfg_getter!` | Делегирование административных конфигурационных getter через общий `ServerAppState` |
| `location::Location` | Добавление location context к административным error enum там, где это соответствует текущей error-модели workspace |
| `optml::Optml` | Сохранение принятой в workspace оптимизации и нормализации derive-списков |
| `naming_macros` и `token_patterns_macros` | Использование внутри генераторов для единообразного формирования имён и повторяемых token patterns; не как административная бизнес-логика |

Вспомогательные proc-macro `pg_crud_cmn_macros`, `pg_crud_macros_cmn_macros`, `gen_derive_ts_builder`, `gen_quotes`, `to_err_string_macros` и связанные macro-helper crate следует переиспользовать через существующий стек генерации. Административный crate не должен дублировать их внутреннюю работу.

Граница генерации:

- proc-macro генерируют структурно повторяемый код;
- ручной код содержит только security-sensitive и предметные инварианты;
- хеширование паролей, проверка JWT, CSRF, принятие решения RBAC, защита последнего администратора и транзакционная семантика остаются явно видимым Rust-кодом;
- proc-macro могут генерировать точки подключения к этим политикам, но не должны скрывать security-решения внутри неявного шаблона.

Перед реализацией таблиц необходимо сначала довести генераторы до возможностей, нужных всей админке, а затем использовать их одинаково во всех административных сущностях. Это позволит избежать ручных расхождений между API, SQL, OpenAPI и клиентскими функциями.

### 2.2. Расширить `gen_pg_types` для административных типов

В `gen_pg_types_src` следует добавить или проверить генерацию:

- owned и borrowed wrapper-представлений;
- `From` и `TryFrom` для разрешённых входных типов;
- `AsRef` для строк, byte slice и PostgreSQL-типов;
- `Display` только для несекретных типов;
- `Debug` с делегированием только для несекретных типов;
- `serde::Serialize`, `serde::Deserialize`, `schemars::JsonSchema` и `utoipa::ToSchema` по явной конфигурации;
- SQLx `Type`, `Encode` и `Decode` для поддерживаемых PostgreSQL-типов;
- nullable/non-null вариантов;
- ограничений длины и проверок строкового формата;
- запрета генерации `Serialize`, `Display` и обычного `Debug` для password, token, JWT secret и hash wrapper-типов;
- redacted `Debug` для секретных wrapper-типов;
- compile-time тестов набора сгенерированных trait implementation.

Для административных идентификаторов нужно переиспользовать уже существующие PostgreSQL-типы, если их семантика совпадает. Отдельный тип создаётся только для различимой доменной семантики, а не для повторения одинакового SQL-представления.

### 2.3. Расширить `gen_pg_tbl` для административных таблиц

В `gen_pg_tbl_src` следует добавить или проверить поддержку следующих декларативных настроек поля и таблицы:

- исключение поля из create, read, update или delete DTO;
- write-only поле для входного пароля;
- полное исключение `password_hash`, token hash и иных секретов из API и OpenAPI;
- immutable и server-generated поля;
- singleton-таблица для `admin_system_settings`;
- append-only таблица для `admin_audit_log`;
- read-only таблица или read-only API для системных permissions;
- отдельные разрешения для каждой CRUD-операции;
- декларативный permission prefix таблицы;
- route metadata для auth/RBAC middleware;
- транзакционные before/after hooks для проверки инвариантов и записи аудита;
- custom validation hook до выполнения SQL;
- custom response mapping без раскрытия внутренней модели БД;
- отзыв связанных сессий после изменения пароля или блокировки пользователя;
- защита системных записей через явно подключаемую policy-функцию;
- OpenAPI security requirements, `401`, `403`, `409`, `422` и `429`;
- генерация типизированных frontend/client функций из того же route contract;
- регистрация маршрутов и OpenAPI-компонентов через единый generated descriptor;
- генерация тестовых cases для маршрутов, схем, SQL bind order и отсутствия секретных полей.

Hooks должны быть обычными явно типизированными функциями, передаваемыми генератору, а не строковыми фрагментами Rust-кода. Генератор отвечает за вызов hook в правильной точке и за распространение ошибки, а реализация security-инварианта остаётся в административном crate.

### 2.4. Зафиксировать порядок macro-first реализации

Для каждой административной сущности используется один порядок:

1. Описать доменные wrapper-типы через `gen_pg_types`, `Newtype`, `BoundedString` и `EnumFromStr`.
2. Описать таблицу декларацией `GenPgTbl`.
3. Сгенерировать SQL, DTO, CRUD, фильтры, маршруты, OpenAPI и клиентские функции.
4. Подключить явно типизированные policy и audit hooks.
5. Написать вручную только операции, которые не являются CRUD: sign-in, refresh, sign-out, `/me`, массовый отзыв сессий и bootstrap.
6. Добавить compile-time и snapshot-тесты generated output.
7. Только после подтверждённого пробела в генераторе писать ручной повторяемый код; такой пробел сначала рассматривается как кандидат на общее расширение proc-macro.

### 3. Спроектировать PostgreSQL-схему

Минимальные таблицы:

```text
admin_users
admin_roles
admin_permissions
admin_user_roles
admin_role_permissions
admin_refresh_tokens
admin_access_sessions
admin_login_attempts
admin_audit_log
admin_system_settings
```

Основные ограничения:

- уникальный логин без учёта регистра;
- пароль хранится только как Argon2id hash;
- запрет пустых имён;
- каскадное удаление связей ролей;
- уникальность пар `user_id + role_id`;
- уникальность пар `role_id + permission_id`;
- срок действия refresh token;
- возможность отзыва access session;
- журнал аудита append-only;
- системную роль администратора нельзя удалить;
- последнего активного администратора нельзя заблокировать или удалить.

Для схемы нужны версионируемые и идемпотентные миграции либо соответствующий `prep_pg`, согласованный с существующим способом подготовки таблиц.

### 4. Использовать упрощённую модель разрешений

Mapcam использует сложную систему `rules`, связанную в том числе с конкретными географическими сущностями. Для универсальной админки она избыточна.

Предлагаются стабильные строковые разрешения:

```text
users:read
users:create
users:update
users:delete

roles:read
roles:create
roles:update
roles:delete

permissions:read
role_permissions:update
user_roles:update

audit_log:read
system_settings:read
system_settings:update
metrics:read
openapi:read
```

В Rust разрешение должно быть enum, а не произвольной строкой на доменной границе. Преобразование между БД и enum выполняется через `TryFrom`.

При добавлении новых прикладных таблиц генератор сможет регистрировать дополнительные разрешения:

```text
orders:read
orders:create
orders:update
orders:delete
```

### 5. Добавить доменные типы

Для административных полей понадобятся wrapper-типы:

- `AdminUserId`;
- `AdminRoleId`;
- `AdminPermissionId`;
- `AdminLogin`;
- `AdminDisplayName`;
- `AdminPassword`;
- `AdminPasswordHash`;
- `AdminSessionId`;
- `AdminRefreshToken`;
- `AdminPermissionName`;
- `AdminAuditAction`;
- `AdminAuditResource`.

Сырые `String`, `i64`, UUID и типы внешних библиотек не должны выходить на доменные границы. Часть wrapper-типов можно генерировать через существующие `gen_pg_types` и `newtype`.

### 6. Сгенерировать обычный CRUD

Через `gen_pg_tbl` можно построить типовую часть API для:

- пользователей;
- ролей;
- разрешений;
- связей пользователей и ролей;
- связей ролей и разрешений;
- журнала аудита.

Генератор может предоставить:

- create/read/update/delete payload;
- фильтры;
- сортировку;
- пагинацию;
- SQL;
- Axum routes;
- DTO;
- OpenAPI schemas;
- клиентские функции.

Над сгенерированным CRUD необходим отдельный слой бизнес-логики для паролей, системной роли, сессий и аудита.

До объявления административных таблиц должны быть реализованы общие расширения из пунктов 2.2 и 2.3. Все административные таблицы должны использовать один и тот же generated route descriptor, чтобы runtime routes, OpenAPI и клиентские функции не могли разойтись.

### 7. Реализовать безопасное хранение паролей

Следует перенести подход Mapcam:

- Argon2id;
- уникальная соль;
- ограничение параллельного хеширования;
- выполнение CPU-intensive хеширования через `spawn_blocking`;
- отсутствие пароля и password hash в ответах API;
- одинаковый внешний ответ для неизвестного логина и неправильного пароля;
- возможность обновлять параметры Argon2 без изменения API.

Для этого в workspace, вероятно, понадобится зависимость `argon2`.

### 8. Реализовать сессии

Рекомендованная схема:

- короткоживущий access JWT;
- долгоживущий refresh token;
- refresh token хранится в БД только как hash;
- access session регистрируется в БД и может быть отозвана;
- оба токена передаются через `HttpOnly` cookies;
- `Secure` включается в production;
- применяется `SameSite=Lax` или `SameSite=Strict`;
- logout отзывает текущую сессию;
- блокировка пользователя отзывает все его сессии.

JWT и refresh token нельзя сохранять в `localStorage` или `sessionStorage`.

Для JWT потребуется добавить workspace-зависимость `jsonwebtoken` либо реализовать другой подписанный формат. Предпочтительнее использовать проверенную библиотеку.

### 9. Защитить mutating-запросы от CSRF

Для `POST`, `PUT`, `PATCH` и `DELETE`:

- проверять `Origin`;
- использовать CSRF token, связанный с сессией;
- требовать отдельный заголовок, например `X-CSRF-Token`;
- не принимать mutating-запрос только на основании cookie.

CORS должен разрешать credentials только для явно настроенных origin. Значение `*` нельзя совмещать с credential cookies.

### 10. Добавить auth API

Предлагаемые маршруты:

```text
POST   /api/v1/admin/auth/sign-in
POST   /api/v1/admin/auth/refresh
POST   /api/v1/admin/auth/sign-out
GET    /api/v1/admin/auth/me
GET    /api/v1/admin/auth/sessions
DELETE /api/v1/admin/auth/sessions/:id
DELETE /api/v1/admin/auth/sessions
```

`/me` возвращает:

- идентификатор;
- логин;
- отображаемое имя;
- роли;
- эффективные разрешения.

Маршруты auth не являются обычным табличным CRUD и реализуются вручную, но их request/response wrapper-типы, OpenAPI schema fragments, error contracts и клиентские функции должны собираться существующими macro-helper средствами. Если текущий стек не умеет описывать нетабличный route contract, сначала следует добавить общий proc-macro или расширение существующего генератора маршрутов, а не создавать семь несвязанных комплектов backend/OpenAPI/client-кода.

### 11. Добавить middleware аутентификации

Middleware должен:

1. Извлечь access token.
2. Проверить подпись, issuer, audience и срок действия.
3. Проверить наличие активной сессии в БД.
4. Проверить, что пользователь не заблокирован.
5. Создать `AuthenticatedAdmin`.
6. Поместить его в request extensions.
7. Для mutating-операций проверить CSRF.
8. Для конкретного маршрута проверить разрешение.

Публичными оставить только:

- sign-in;
- refresh;
- health check;
- необходимые статические файлы.

Swagger можно сделать публичным в development или доступным по разрешению `openapi:read`.

### 12. Реализовать RBAC-проверки

Для каждого административного обработчика должно быть явно указано требуемое разрешение:

```text
GET    /admin/users      -> users:read
POST   /admin/users      -> users:create
PATCH  /admin/users      -> users:update
DELETE /admin/users      -> users:delete
GET    /admin/audit-log  -> audit_log:read
PATCH  /admin/settings   -> system_settings:update
```

Проверка должна выполняться сервером. Скрытие кнопки во frontend является только улучшением интерфейса, но не механизмом безопасности.

Permission metadata должна генерироваться `gen_pg_tbl` вместе с маршрутом. Middleware использует сгенерированный descriptor, поэтому HTTP handler, OpenAPI и frontend client получают одно и то же имя разрешения из одного источника.

### 13. Добавить специальные операции с пользователями

Поверх типового CRUD:

- создание пользователя с хешированием пароля;
- изменение пароля;
- блокировка и разблокировка;
- массовый отзыв сессий;
- назначение ролей в транзакции;
- запрет удалить текущего пользователя без специального подтверждения;
- запрет удалить или заблокировать последнего администратора;
- исключение password hash из всех read-моделей.

### 14. Добавить управление ролями

Нужны страницы и API:

```text
/admin/roles
/admin/roles/:id
/admin/roles/:id/permissions
/admin/users/:id/roles
```

Особые правила:

- системную роль `admin` нельзя удалить;
- роль нельзя удалить, если это оставит систему без администратора;
- системные разрешения нельзя переименовывать через API;
- изменять можно набор разрешений роли.

### 15. Добавить аудит

Каждая значимая операция записывает:

- пользователя;
- действие;
- ресурс;
- идентификатор ресурса;
- request ID;
- время;
- безопасные детали изменения;
- результат операции.

Пароли, JWT, cookie, секреты и password hash в аудит не записываются.

Для атомарности изменение данных и запись аудита должны выполняться в одной PostgreSQL-транзакции.

### 16. Добавить системные настройки без географии

Вместо Mapcam-полей оставить:

- `site_name`;
- `tab_title`;
- `main_logo`;
- `primary_color`;
- `default_admin_route`;
- `organization_name`;
- `organization_contacts`;
- `support_url`;
- `updated_at`.

Настройки лучше хранить как типизированную singleton-запись, а не как полностью произвольный JSON.

### 17. Собрать OpenAPI

Текущий `server_tbl_example` уже доказывает, что генератор умеет выдавать CRUD paths и schemas.

Нужно объединить в один документ:

- auth routes;
- users;
- roles;
- permissions;
- user-role links;
- role-permission links;
- audit log;
- system settings;
- общие error responses.

В OpenAPI добавить:

- cookie security scheme;
- CSRF header;
- ответы `401`, `403`, `409`, `413`, `422`, `429`, `500`;
- примеры запросов;
- описание необходимых разрешений.

OpenAPI должен формироваться из route descriptors, сгенерированных `gen_pg_tbl` и macro-helper стеком для нетабличных auth routes. Ручное повторное перечисление административных paths и schemas в `server` не допускается.

### 18. Вынести Swagger UI из inline HTML

Сейчас HTML Swagger находится прямо в `server/src/main.rs`. Документацию лучше оформить отдельными маршрутами административного модуля:

```text
/admin/swagger-ui
/admin/openapi.json
```

Также желательно:

- не зависеть от CDN в production;
- обеспечить совместимую с CSP загрузку ресурсов;
- ограничить доступ разрешением `openapi:read`.

### 19. Перенести frontend как отдельную admin SPA

Из Mapcam можно переиспользовать общие идеи и часть JavaScript:

- `01_lib.js`;
- `02_api.js`;
- pagination/filter helpers;
- card/form helpers;
- auth pages;
- users pages;
- роли и правила;
- operational pages;
- feedback/view helpers.

Не переносить:

- map page;
- Leaflet и географические библиотеки;
- projects, layers, features и properties;
- cameras и screenshots;
- WFS;
- tile pages;
- географическую client configuration.

Следует переименовать сущности Mapcam и удалить все глобальные константы, относящиеся к геосистеме, а не оставлять неиспользуемый код.

### 20. Добавить маршруты frontend

Предлагаемая структура:

```text
/admin/sign-in
/admin
/admin/users
/admin/users/:id
/admin/roles
/admin/roles/:id
/admin/permissions
/admin/audit-log
/admin/system-settings
/admin/metrics
/admin/version
/admin/swagger-ui
```

`/admin` должен перенаправлять на первую разрешённую пользователю страницу.

### 21. Интегрировать frontend в Router

Сейчас API целиком вложен в `/api/v1`. Административную SPA лучше монтировать отдельно:

```text
/api/v1/admin/...  backend
/admin/...         frontend
/admin/assets/...  static files
```

Так SPA fallback не сможет перехватить неизвестные API-маршруты.

### 22. Расширить конфигурацию

Понадобятся domain-wrapper параметры:

- JWT secret;
- access token TTL;
- refresh token TTL;
- cookie secure mode;
- allowed origins;
- sign-in rate limit;
- session limit на пользователя;
- bootstrap administrator login;
- bootstrap administrator password или одноразовый bootstrap token;
- флаг доступности Swagger.

Секреты должны использовать `secrecy` и не попадать в `Debug`.

### 23. Безопасно создать первого администратора

Не следует переносить из Mapcam захешированный пароль администратора в seed-файл.

Возможные варианты:

1. Одноразовый bootstrap через environment.
2. Отдельная CLI-команда создания администратора.
3. Startup bootstrap только при пустой таблице пользователей.

Предпочтителен второй вариант. Если нужен автоматический deployment, подойдёт первый вариант с обязательным удалением bootstrap secret после создания пользователя.

### 24. Добавить rate limiting

Счётчики можно держать в PostgreSQL для согласованности между несколькими экземплярами сервера.

Оптимальный порядок реализации:

1. Зафиксировать macro coverage тестами текущего generated API.
2. Расширить `gen_pg_types_src` для административных и секретных wrapper-типов.
3. Расширить `gen_pg_tbl_src` для sensitive fields, permissions, hooks, audit и OpenAPI security.
4. Добавить compile-time и generated-output тесты proc-macro.
5. Реализовать схему БД и доменные типы только через обновлённый macro-first стек.
6. Реализовать bootstrap администратора.
7. Реализовать хеширование паролей.
8. Реализовать sign-in, refresh, logout и `/me`.
9. Подключить auth middleware и CSRF.
10. Подключить permissions и RBAC через generated route metadata.
11. Сгенерировать пользователей.
12. Сгенерировать роли и связи.
13. Сгенерировать Audit log с append-only политикой.
14. Сгенерировать System settings как singleton resource.
15. Собрать OpenAPI из generated descriptors.

- проверить детерминированность proc-macro output.

## Итоговое архитектурное решение

Следует реализовать не копию Mapcam с удалёнными географическими страницами, а отдельный `server_admin` с упрощённой универсальной RBAC-моделью. Основой реализации должен быть текущий proc-macro стек workspace: `gen_pg_types` формирует доменные PostgreSQL-wrapper типы, `gen_pg_tbl` формирует согласованные SQL, CRUD, routes, OpenAPI и client contracts, а ручной код отвечает только за явно видимые security-sensitive политики. Такая админка сможет подключаться к новым таблицам без дублирования типовой логики и без переноса географической архитектуры Mapcam.
