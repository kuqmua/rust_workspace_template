# План реализации полноценной административной панели

## Цель

Добавить в `server` полноценную административную панель, основанную на архитектурных решениях из `/home/sergey/projects/mapcam_rust`, но не переносить географическую предметную область, PostGIS и связанные с картой функции.

Текущий workspace уже содержит подходящую основу: Axum, PostgreSQL, генерируемый CRUD, OpenAPI, Swagger UI, application state, middleware безопасности и метрики.

Не следует напрямую переносить crate `shared` из Mapcam: он тесно связан с проектами, слоями, геометрией, PostGIS, файлами объектов и картографическими разрешениями. Следует перенести архитектурные решения и адаптировать административную часть к генераторам этого workspace.

## Подробный план

### 1. Зафиксировать границы административного модуля

Административная часть не должна знать о географии. Из Mapcam не переносить:

- PostGIS;
- проекты и группы проектов;
- слои и группы слоёв;
- геометрические объекты;
- свойства и значения объектов;
- тайлы;
- WFS;
- карты;
- камеры;
- скриншоты;
- географические поля системных настроек.

Оставить общую модель:

```text
auth
users
roles
permissions
user_roles
role_permissions
sessions
login_attempts
audit_log
system_settings
metrics
openapi
```

### 2. Разделить административную логику по архитектурным границам

Общую логику следует вынести из бинарного `server`.

Предлагаемая структура:

```text
server
  только запуск, конфигурация и сборка общего Router

server_admin
  административные таблицы
  бизнес-логика
  API
  авторизация
  RBAC
  аудит
  OpenAPI

server_admin_frontend
  SPA
  статические ресурсы
  маршруты страниц
```

Если нежелательно создавать два crate, минимальный вариант — один `server_admin`, содержащий API и frontend. Разделение backend и frontend предпочтительнее.

Создание новых crate и добавление зависимостей должно быть явно разрешено при переходе к реализации.

### 3. Спроектировать PostgreSQL-схему

Минимальные таблицы:

```text
admin_users
admin_roles
admin_permissions
admin_user_roles
admin_role_permissions
admin_refresh_tokens
admin_access_sessions
admin_login_attempts
admin_audit_log
admin_system_settings
```

Основные ограничения:

- уникальный логин без учёта регистра;
- пароль хранится только как Argon2id hash;
- запрет пустых имён;
- каскадное удаление связей ролей;
- уникальность пар `user_id + role_id`;
- уникальность пар `role_id + permission_id`;
- срок действия refresh token;
- возможность отзыва access session;
- журнал аудита append-only;
- системную роль администратора нельзя удалить;
- последнего активного администратора нельзя заблокировать или удалить.

Для схемы нужны версионируемые и идемпотентные миграции либо соответствующий `prep_pg`, согласованный с существующим способом подготовки таблиц.

### 4. Использовать упрощённую модель разрешений

Mapcam использует сложную систему `rules`, связанную в том числе с конкретными географическими сущностями. Для универсальной админки она избыточна.

Предлагаются стабильные строковые разрешения:

```text
users:read
users:create
users:update
users:delete

roles:read
roles:create
roles:update
roles:delete

permissions:read
role_permissions:update
user_roles:update

audit_log:read
system_settings:read
system_settings:update
metrics:read
openapi:read
```

В Rust разрешение должно быть enum, а не произвольной строкой на доменной границе. Преобразование между БД и enum выполняется через `TryFrom`.

При добавлении новых прикладных таблиц генератор сможет регистрировать дополнительные разрешения:

```text
orders:read
orders:create
orders:update
orders:delete
```

### 5. Добавить доменные типы

Для административных полей понадобятся wrapper-типы:

- `AdminUserId`;
- `AdminRoleId`;
- `AdminPermissionId`;
- `AdminLogin`;
- `AdminDisplayName`;
- `AdminPassword`;
- `AdminPasswordHash`;
- `AdminSessionId`;
- `AdminRefreshToken`;
- `AdminPermissionName`;
- `AdminAuditAction`;
- `AdminAuditResource`.

Сырые `String`, `i64`, UUID и типы внешних библиотек не должны выходить на доменные границы. Часть wrapper-типов можно генерировать через существующие `gen_pg_types` и `newtype`.

### 6. Сгенерировать обычный CRUD

Через `gen_pg_tbl` можно построить типовую часть API для:

- пользователей;
- ролей;
- разрешений;
- связей пользователей и ролей;
- связей ролей и разрешений;
- журнала аудита.

Генератор может предоставить:

- create/read/update/delete payload;
- фильтры;
- сортировку;
- пагинацию;
- SQL;
- Axum routes;
- DTO;
- OpenAPI schemas;
- клиентские функции.

Над сгенерированным CRUD необходим отдельный слой бизнес-логики для паролей, системной роли, сессий и аудита.

### 7. Реализовать безопасное хранение паролей

Следует перенести подход Mapcam:

- Argon2id;
- уникальная соль;
- ограничение параллельного хеширования;
- выполнение CPU-intensive хеширования через `spawn_blocking`;
- отсутствие пароля и password hash в ответах API;
- одинаковый внешний ответ для неизвестного логина и неправильного пароля;
- возможность обновлять параметры Argon2 без изменения API.

Для этого в workspace, вероятно, понадобится зависимость `argon2`.

### 8. Реализовать сессии

Рекомендованная схема:

- короткоживущий access JWT;
- долгоживущий refresh token;
- refresh token хранится в БД только как hash;
- access session регистрируется в БД и может быть отозвана;
- оба токена передаются через `HttpOnly` cookies;
- `Secure` включается в production;
- применяется `SameSite=Lax` или `SameSite=Strict`;
- logout отзывает текущую сессию;
- блокировка пользователя отзывает все его сессии.

JWT и refresh token нельзя сохранять в `localStorage` или `sessionStorage`.

Для JWT потребуется добавить workspace-зависимость `jsonwebtoken` либо реализовать другой подписанный формат. Предпочтительнее использовать проверенную библиотеку.

### 9. Защитить mutating-запросы от CSRF

Для `POST`, `PUT`, `PATCH` и `DELETE`:

- проверять `Origin`;
- использовать CSRF token, связанный с сессией;
- требовать отдельный заголовок, например `X-CSRF-Token`;
- не принимать mutating-запрос только на основании cookie.

CORS должен разрешать credentials только для явно настроенных origin. Значение `*` нельзя совмещать с credential cookies.

### 10. Добавить auth API

Предлагаемые маршруты:

```text
POST   /api/v1/admin/auth/sign-in
POST   /api/v1/admin/auth/refresh
POST   /api/v1/admin/auth/sign-out
GET    /api/v1/admin/auth/me
GET    /api/v1/admin/auth/sessions
DELETE /api/v1/admin/auth/sessions/:id
DELETE /api/v1/admin/auth/sessions
```

`/me` возвращает:

- идентификатор;
- логин;
- отображаемое имя;
- роли;
- эффективные разрешения.

### 11. Добавить middleware аутентификации

Middleware должен:

1. Извлечь access token.
2. Проверить подпись, issuer, audience и срок действия.
3. Проверить наличие активной сессии в БД.
4. Проверить, что пользователь не заблокирован.
5. Создать `AuthenticatedAdmin`.
6. Поместить его в request extensions.
7. Для mutating-операций проверить CSRF.
8. Для конкретного маршрута проверить разрешение.

Публичными оставить только:

- sign-in;
- refresh;
- health check;
- необходимые статические файлы.

Swagger можно сделать публичным в development или доступным по разрешению `openapi:read`.

### 12. Реализовать RBAC-проверки

Для каждого административного обработчика должно быть явно указано требуемое разрешение:

```text
GET    /admin/users      -> users:read
POST   /admin/users      -> users:create
PATCH  /admin/users      -> users:update
DELETE /admin/users      -> users:delete
GET    /admin/audit-log  -> audit_log:read
PATCH  /admin/settings   -> system_settings:update
```

Проверка должна выполняться сервером. Скрытие кнопки во frontend является только улучшением интерфейса, но не механизмом безопасности.

### 13. Добавить специальные операции с пользователями

Поверх типового CRUD:

- создание пользователя с хешированием пароля;
- изменение пароля;
- блокировка и разблокировка;
- массовый отзыв сессий;
- назначение ролей в транзакции;
- запрет удалить текущего пользователя без специального подтверждения;
- запрет удалить или заблокировать последнего администратора;
- исключение password hash из всех read-моделей.

### 14. Добавить управление ролями

Нужны страницы и API:

```text
/admin/roles
/admin/roles/:id
/admin/roles/:id/permissions
/admin/users/:id/roles
```

Особые правила:

- системную роль `admin` нельзя удалить;
- роль нельзя удалить, если это оставит систему без администратора;
- системные разрешения нельзя переименовывать через API;
- изменять можно набор разрешений роли.

### 15. Добавить аудит

Каждая значимая операция записывает:

- пользователя;
- действие;
- ресурс;
- идентификатор ресурса;
- request ID;
- время;
- безопасные детали изменения;
- результат операции.

Пароли, JWT, cookie, секреты и password hash в аудит не записываются.

Для атомарности изменение данных и запись аудита должны выполняться в одной PostgreSQL-транзакции.

### 16. Добавить системные настройки без географии

Вместо Mapcam-полей оставить:

- `site_name`;
- `tab_title`;
- `main_logo`;
- `primary_color`;
- `default_admin_route`;
- `organization_name`;
- `organization_contacts`;
- `support_url`;
- `updated_at`.

Настройки лучше хранить как типизированную singleton-запись, а не как полностью произвольный JSON.

### 17. Собрать OpenAPI

Текущий `server_tbl_example` уже доказывает, что генератор умеет выдавать CRUD paths и schemas.

Нужно объединить в один документ:

- auth routes;
- users;
- roles;
- permissions;
- user-role links;
- role-permission links;
- audit log;
- system settings;
- общие error responses.

В OpenAPI добавить:

- cookie security scheme;
- CSRF header;
- ответы `401`, `403`, `409`, `413`, `422`, `429`, `500`;
- примеры запросов;
- описание необходимых разрешений.

### 18. Вынести Swagger UI из inline HTML

Сейчас HTML Swagger находится прямо в `server/src/main.rs`. Документацию лучше оформить отдельными маршрутами административного модуля:

```text
/admin/swagger-ui
/admin/openapi.json
```

Также желательно:

- не зависеть от CDN в production;
- обеспечить совместимую с CSP загрузку ресурсов;
- ограничить доступ разрешением `openapi:read`.

### 19. Перенести frontend как отдельную admin SPA

Из Mapcam можно переиспользовать общие идеи и часть JavaScript:

- `01_lib.js`;
- `02_api.js`;
- pagination/filter helpers;
- card/form helpers;
- auth pages;
- users pages;
- роли и правила;
- operational pages;
- feedback/view helpers.

Не переносить:

- map page;
- Leaflet и географические библиотеки;
- projects, layers, features и properties;
- cameras и screenshots;
- WFS;
- tile pages;
- географическую client configuration.

Следует переименовать сущности Mapcam и удалить все глобальные константы, относящиеся к геосистеме, а не оставлять неиспользуемый код.

### 20. Добавить маршруты frontend

Предлагаемая структура:

```text
/admin/sign-in
/admin
/admin/users
/admin/users/:id
/admin/roles
/admin/roles/:id
/admin/permissions
/admin/audit-log
/admin/system-settings
/admin/metrics
/admin/version
/admin/swagger-ui
```

`/admin` должен перенаправлять на первую разрешённую пользователю страницу.

### 21. Интегрировать frontend в Router

Сейчас API целиком вложен в `/api/v1`. Административную SPA лучше монтировать отдельно:

```text
/api/v1/admin/...  backend
/admin/...         frontend
/admin/assets/...  static files
```

Так SPA fallback не сможет перехватить неизвестные API-маршруты.

### 22. Расширить конфигурацию

Понадобятся domain-wrapper параметры:

- JWT secret;
- access token TTL;
- refresh token TTL;
- cookie secure mode;
- allowed origins;
- sign-in rate limit;
- session limit на пользователя;
- bootstrap administrator login;
- bootstrap administrator password или одноразовый bootstrap token;
- флаг доступности Swagger.

Секреты должны использовать `secrecy` и не попадать в `Debug`.

### 23. Безопасно создать первого администратора

Не следует переносить из Mapcam захешированный пароль администратора в seed-файл.

Возможные варианты:

1. Одноразовый bootstrap через environment.
2. Отдельная CLI-команда создания администратора.
3. Startup bootstrap только при пустой таблице пользователей.

Предпочтителен второй вариант. Если нужен автоматический deployment, подойдёт первый вариант с обязательным удалением bootstrap secret после создания пользователя.

### 24. Добавить rate limiting

Отдельные ограничения нужны для:

- sign-in по IP;
- sign-in по паре IP и login;
- refresh;
- mutating admin API;
- тяжёлых read-запросов аудита.

Счётчики можно держать в PostgreSQL для согласованности между несколькими экземплярами сервера.

### 29. Выполнить финальную проверку

Перед завершением реализации:

```bash
cargo fmt
cargo clippy --all-targets --all-features -- -D warnings
cargo test -p tests code_style
cargo test --workspace
```

Дополнительно:

- проверить OpenAPI валидатором;
- проверить отсутствие географических маршрутов и зависимостей;
- проверить, что секреты не сериализуются и не логируются;
- проверить security headers и cookie;
- проверить работу SPA после прямого открытия вложенного URL;
- проверить создание чистой БД с нуля.

## Итоговое архитектурное решение

Следует реализовать не копию Mapcam с удалёнными географическими страницами, а отдельный `server_admin` с упрощённой универсальной RBAC-моделью. Такая админка сможет подключаться к новым таблицам через `gen_pg_tbl`, не затягивая в шаблон географическую архитектуру Mapcam.
